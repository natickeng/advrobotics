# Part 1: How it works

## Building on, not replacing, Project 03

You already have working motor-power code from Project 03. This project wraps that code in a loop that reads a controller and decides what power to send, instead of running a fixed script. Give Ollama your movement code from Project 03 as a starting point rather than describing the whole thing from scratch — it'll produce better results building on code that's already proven to work on your robot.

## What you're working with

The PRIZM Tele-Op module pairs with a DUALSHOCK 4 (PS4) controller over Bluetooth:

- Hold **Share + Power** on the controller for 5 seconds to enter discovery mode, then press the **Black Button** on the Tele-Op module — a solid green LED means it's paired.
- Joystick input needs a **dead zone** — a small range near center that reads as zero — because the sticks don't rest at a perfect, identical zero every time. Without one, your robot creeps or drifts even when you're not touching anything.
- The PRIZM API includes drive-mode speed scaling as a reference pattern: a low-speed "crawl" mode, a default "normal" mode, and a high-speed "turbo" mode, switched by buttons. You don't have to copy this exactly, but it's worth knowing this pattern exists — precision driving and fast driving want different power scales, and giving the driver a way to switch is more useful than picking one fixed speed.

## Real-time means every loop matters

Movement code in Project 03 ran a script from start to finish. This code runs forever, checking the controller every pass through the loop and reacting immediately. That changes what "working" means — the test below isn't about reaching an endpoint, it's about responsiveness: does the robot react to input right now, or is there a lag that makes it feel disconnected from the stick?

# Part 2: Do the work

## Step 1: Read the controller

Direct Ollama to write code that reads the controller's joystick and button state each loop, using your movement code as the base for how motor power actually gets sent.

## Step 2: Add a dead zone

Without one, test this yourself: let go of the sticks completely and watch whether the robot sits still. If it creeps, that's your dead zone problem — the fix is to treat any joystick reading inside a small range around center as exactly zero.

## Step 3: Wire joystick position to drive direction

Forward/backward on one stick should map cleanly to forward/backward power; strafe or turn (whichever your drivetrain needs) maps the other axis. Test each direction individually before combining them.

## The test (checked at your demo)

Hand the controller over for your demo. It passes if:

1. The robot responds to stick movement with no perceptible lag — pushing the stick and seeing the robot move should feel immediate, not delayed.
2. Letting go of both sticks brings the robot to a complete stop and keeps it there — no drift, no creep.
3. Forward/backward/turn (or strafe, if your drivetrain supports it) all map to the directions you'd expect, without having to think about it.
